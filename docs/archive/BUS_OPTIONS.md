# Bus options: the rear expansion port or the HuCard slot

Decision on 2026-11-19, superseding the hand-off's assumption that stage 1 must be
a rear-port board. Both connectors are taps on the same CPU bus, so the question
is not capability but cost, power, mechanics and what the console will let a card
do. Both pinouts are committed as data (`docs/ext_bus_pinout.csv`,
`docs/hucard_pinout.csv`) and generated by `tools/ext_bus.py` and
`tools/hucard_bus.py`.

**Decision: stage 1 is built on the card edge**, and the same board grows into a
HuCard flash card. The rear-port board stays in the repo as the full variant. This
architecture is not speculative: it ships (§10).

## 1. What each connector carries

| | rear port (3×23) | card edge (38) |
|---|---|---|
| address | A0–A20, all 21 | A0–A20, all 21 |
| data | D0–D7 | D0–D7 |
| strobes | /RD, /WR | /RD, /WR |
| reset | /RESET | /RST |
| IRQ2 | in (b21) | **out** (37) — the card can raise it |
| HSM (7.16 MHz flag) | b3 | 35 |
| RDY (wait states) | b20 | — |
| clock | DCK (a9) | — |
| CD presence (K7) | b2 | — |
| audio | AudioL, AudioC, AudioR | AUDIO IN, mono |
| card detect | /CARD (c3) | /CD (1), card grounds it |
| power | **+5A only** (analog video rail) | **+5V** |
| other | VDC/VCE video buses, /NMI, CESEL, /CEK | — |

The card edge is missing three things the port has: **stereo audio, K7 and RDY**.
It gains **a real 5 V supply** and an **outbound IRQ2**.

## 2. Where the CD hardware has to live

From [STAGE2_REFERENCE.md](../STAGE2_REFERENCE.md) §2, the windows a CD emulator
must answer:

| what | physical | A20 |
|---|---|---|
| CD registers | `$1FF800–$1FF8FF` | 1 |
| CD work RAM, 64 KB | `$100000–$10FFFF` | 1 |
| Backup RAM, 2 KB | `$1EE000–$1EE7FF` | 1 |
| Super System Card RAM, 192 KB | `$0D0000–$0FFFFF` | 0 |

**Three of the four are above the card's selection window.** The wiki records
`PA20` as a card's `/CE`, so a dumb ROM card only answers the first megabyte. Any
card that wants to be a CD system must therefore drive bus cycles the console
never selects it for.

That is not a new problem and not a geometry problem: the rear port has no chip
select either ("the CPU has no chip enable for this block, reserved for
extension", HuC6280 manual p. 12 — [STAGE2_REFERENCE.md](../STAGE2_REFERENCE.md) §2).
Both boards decode `A20–A8` themselves and drive the data bus on their own
authority. On a console with no CD unit, nothing else answers there.

## 3. A card writing to the bus is proven hardware

The 192 KB at `$0D0000–$0FFFFF` is not hypothetical: it lives **inside the Super
System Card** — same connector, written by the same CPU, through the same strobes.
So the card edge's write path, drive levels and loading are proven by a product,
not by an inference. The only untested act is driving cycles *outside* `/CE`, and
that act is identical whether it comes from the card or from the port.

## 4. What the card route buys

| win | why it matters here |
|---|---|
| **+5 V digital supply** | removes STAGE1 decision 5 — running the bus-side translators from `+5A` and watching for video noise was an open scope test. Gone. |
| **No System Card needed** | the hand-off needs a System Card in the slot for the BIOS and the 192 KB. With the FPGA in the slot, that card is us — no $200+ card to buy, and STAGE2's "make `$68–$7F` switchable or two devices drive the bus" hazard disappears. |
| **Stage 1 can test itself** | the test program lives in our own ROM window. TEST_PLAN T8's "the program loads from a flash HuCard; writing it is its own task" — and the flash card, and the programmer — vanish. |
| **One connector fewer** | the port board needs a 3×23 female header and a way to hang off the back. The console *is* the socket. |
| **It is a flash card** | `$000000–$0FFFFF` is card territory: the same board presents HuCard ROMs from microSD. One device replaces a flash cart and, later, a CD drive. |

## 5. What it costs

| cost | how bad |
|---|---|
| **mono audio** | The card has one AUDIO IN pin, mixed into both channels; CD-DA through the console would be mono. **Acceptable only because phase 2 already outputs its own audio over HDMI/I2S** — see [EARLIER-NOTES-2026-11-04.md](EARLIER-NOTES-2026-11-04.md) ("the console's own audio is simply not used"). If stereo through the console's AV out ever matters, that is the port's job. |
| **no K7** | CD presence is port pin b2. Not needed **if our own firmware** stands in for the System Card. But the BIOS is user-supplied (a real System Card image), and the MiSTer core's only CD-presence signal is K7 (`pce_top.vhd` line 293), so **the real BIOS may check it**, as may a game that polls port K. **Unmeasured**: check the BIOS's boot code first (it's one image, not many discs), then a few discs' loaders. If it checks, the EverDrive's answer applies: it runs the real BIOS on the card alone, so read how it handles K7 before assuming the port board is needed. |
| **no RDY** | wait states are unavailable, so the data must be ready in the cycle. The sim says it is, with ~85 ns to spare against the model's ~140 ns latch point ([STAGE1.md](STAGE1.md) §7). |
| **driving outside `/CE` is undocumented** | the console's documents don't say it is tolerated, but a shipping cart does it ([REFERENCE-EVERDRIVE-PRO.md](../REFERENCE-EVERDRIVE-PRO.md) §2); it is the same decode the port needs, but it is worth one scope probe before the carrier is ordered (TEST_PLAN T4b). |
| **region data order** | the wiki says D0–D7 ascend on a PC Engine and descend on a TurboGrafx-16. **Answered, and it costs nothing**: the same card serves both, because the difference is a per-byte **bit reversal** — HuConv, the tool that prepares images for the repro cards, emits a TG16 image by mapping bit 0↔7 … 3↔4 (`HuCONV_v1.5/huconv.py` lines 142–152). In the FPGA that is a free mapping, or a setting at load time. |

## 6. The pin budget is not improved, and nobody should claim it is

The constraint is the Tang Nano 20K's **34 header I/Os, 24 of them safe**, not the
connector: 21 address + 8 data + 2 strobes will not fit either way, so the
external decoder (74HCT688) that cuts the address down to a 13-bit window stays.
Swapping 69 pins for 38 changes what the board plugs into, not what the FPGA can
see. Stage 2 gets worse (34–36 pins against 28 safe,
[STAGE2_REFERENCE.md](../STAGE2_REFERENCE.md) §7) — and the flash-cart role needs
~20 address lines, which is the module decision in
[STAGE1-CARD.md](STAGE1-CARD.md) §7.

## 7. Open questions this decision creates

| question | answered by |
|---|---|
| Does the real card edge match the wiki's 38 pins? | TEST_PLAN T1c: continuity from card fingers to the **already verified** rear-port pins — the port is the second source the card pinout otherwise lacks |
| Does the console tolerate a card driving `$1FF800` / `$100000`? | a scope on `/RD`, A20 and D0 during a self-test ROM's read of its own RAM (T4b); then T8 |
| *(removed)* the TG16 data order | answered above: a bit reversal per byte, handled in the FPGA or at image load |
| Do games poll K7 directly? | disassemble a few discs' loader code before stage 2 |
| Card dimensions: thickness, pitch, depth | **known** from a working repro board and the slot drawing — 1.6 mm, 1.27 mm pitch, 0.75 mm fingers, 8.6 mm insertion ([STAGE1-CARD.md](STAGE1-CARD.md) §1); a caliper on a real HuCard confirms it (T1d) |

## 9. What would reverse this

If stereo CD-DA through the console's own AV output turns out to be required, or a
survey shows games polling K7, the card alone cannot supply it: then the port board
is added — which is what the one shipping product does (§10) — and the card stays
the card. This is not either/or.

## 10. It already ships: the Turbo EverDrive Pro

The [Turbo EverDrive Pro](https://krikzz.com/our-products/cartridges/turbo-everdrive-pro.html)
($199, krikzz) is this project's architecture as a commercial product: **one
cartridge in the HuCard slot** that plays HuCard ROMs from SD *and* runs a
**built-in CD-ROM² core**, with Arcade Card functions, save states, Ten no Koe 2
saves and region auto-detection. Its own footnote is the load-bearing fact: the CD
core **stops working if a CD-ROM or Ten no Koe 2 is connected to the expansion
port**, or if the console has a built-in CD-ROM (so it cannot do CD games on a Duo).
The whole CD system is therefore in the cartridge.

What that settles for us:

| question | answer |
|---|---|
| may a card answer `$1FF800` and drive `$100000`? (T4b) | **yes, in the shipping product and in its source**: `bus_oe = cpu.oe & (own windows)`, `/CE` not involved ([REFERENCE-EVERDRIVE-PRO.md](../REFERENCE-EVERDRIVE-PRO.md) §2). T4b now checks our decode and timing only |
| is the card the right host for the CD logic? | yes, which is the decision this document records |
| does a card need a System Card? | no — the device is the System Card, and its BIOS is a file |
| stereo CD-DA from a card alone? | **no** — they say so themselves: "CD and hucard audio doesn't work via RF output" because of the mixing circuit, and they sell the **EDFX**, a **stereo expansion board**, alongside it |
| how are regions handled? | they do "switchless region auto detection" — consistent with §5's bit reversal, done in logic |
| what does it need that we lack? | a **Cyclone IV** and **16 MB PSRAM** on a 6-layer board — i.e. the "bigger module" of [STAGE1-CARD.md](STAGE1-CARD.md) §7, not a different idea |

Better than the product page: the cartridges' **development sources are public and
MIT licensed** ([krikzz/turbo-ed-pro-pub](https://github.com/krikzz/turbo-ed-pro-pub)),
including the bus layer and the mappers. They show the decode — a cart drives data
whenever /RD is low and its own window matches, `/CE` plays no part — and they answer
our `$18C1–$18C7` question. Analysis: [REFERENCE-EVERDRIVE-PRO.md](../REFERENCE-EVERDRIVE-PRO.md).

Two lessons we should keep:

1. **The audio answer is a companion port board, not "make the card do it".** My
   §5 lists mono audio as a cost and HDMI/I2S as the escape; the shipping answer is
   an expansion-port stereo board. That is stage 2's real option list.
2. **Memory is not our limit, pins are.** 2 MB of Arcade Card RAM + 256 KB of CD RAM
   + the BIOS sits comfortably inside the 20K's 8 MB SDRAM. A 20-line address bus
   does not fit in 24 pins. Those are different problems, and only the second one
   is a module decision.
